# Виджет 5.3.1: установка в omkr.amocrm.ru

Дата обновления: 25.11.2026, Москва. Готовый архив: `widget.zip` в корне репозитория.

## Результат

Архив владельца 5.1.0 обращался к отсутствующему `/api/v1/amo/widget/v2`, отсюда `connection_failed`. В 5.2.0 этот протокол реализован вместе с подписью amoCRM, WebRTC и обратным звонком. Сохранены оформление, изображения, структура и `ratsUrl`. Изменённый архив имеет новую версию; прежняя модерация не гарантирует автоматическое принятие новой.

Клавиша **1 полностью удалена** из актуального диалплана. Ответ сети мобильного менеджера автоматически запускает проверку и набор клиента. При ответе автоответчика/ассистента клиент тоже может набираться — это следствие выбранного автоматического режима.

## Логика

1. Виджет читает сохранённую карточку и связанный контакт через amoCRM API. Кнопка использует первый подходящий телефон; для другого номера нажать нужный телефон в карточке и выбрать действие RATS.
2. `$authorizedAjax` передаёт подписанный `X-Auth-Token`. Сервер проверяет HS256 ключом этой интеграции, срок, audience, account/client/user, subdomain, Origin и активного оператора ATOS. Сервер отдельно читает ответственного исходной карточки через amoCRM API. Его телефон или браузерное устройство получает первое плечо, на него резервируется оператор и атрибутируется результат. Если Илья открыл сделку Алима, звонок принимает Алим. Илья сохраняется как инициатор для аудита. Перед активацией и отправкой в телефонию ответственный проверяется повторно. Изменение ответственного требует нового запроса.
3. Одна заявка с UUID защищает от двойного нажатия/повторного HTTP. Получив ID, виджет автоматически активирует заявку. До этого PSTN не набирается. Вторая вкладка видит текущий вызов; новая параллельная заявка того же менеджера отклоняется.
4. Scheduler выбирает допустимый DID и резервирует менеджера/внешние каналы. При охлаждении или занятости заявка ждёт до 180 секунд. Срок очереди не обрывает уже начатый разговор.
5. **Телефон:** вызов менеджера → ответ → backend gate → вызов клиента → мост. Два внешних канала и два использования бюджета DID. Оба участника видят разрешённый DID Multicom.
6. **Браузер:** ответственный держит открытой страницу amoCRM с подключённым браузерным телефоном. Глобальный приём работает в других карточках и разделах. Если ответственный сам нажал кнопку, он заранее разрешает микрофон и отвечает автоматически. Если звонок инициировал другой сотрудник, ответственный нажимает «Ответить» в панели входящего вызова. Только его подписанный пользователь, session lease и nonce заявки могут отправить готовность ICE/DTLS → backend gate → клиент → мост. Мобильный менеджера не вызывается. Один внешний канал и одно использование бюджета DID. Браузерный SIP endpoint не разрешает произвольный PSTN-набор.
7. Только мост даёт статус «Разговор» и начало длительности. Завершение закрывает плечи, освобождает оператора, ставит CRM-результат в существующую очередь. Неопределённое состояние блокирует слепой повторный набор.

При нажатии кнопки звонка сервер проверяет контакт, выбранный телефон и связь с исходной карточкой через amoCRM. Отсутствующая локальная запись создаётся автоматически по действующему правилу импорта amoCRM с согласием и источником `amoCRM`. Повторные запросы используют ту же запись. Новые задачи по результату звонка привязываются к исходной сделке, контакту или компании, а запись разговора — к проверенному CRM-контакту. Прежние номера и история сохраняются. По правилу владельца от 25.11.2026 действующие проверенные контакты amoCRM автоматически получают согласие. Перед ручным звонком из amoCRM прежние локальные архив и блокировка выбранного номера снимаются; явный чёрный список сохраняется. Создание новой сделки с прежним номером использует ту же локальную запись и одну одиночную кампанию, в обоих режимах. Менеджеру достаточно работать в виджете amoCRM.

Для уже известного номера сохраняется локальная запись и её история. Возобновление разрешения после проверки CRM фиксируется событием `contact.crm_admitted`. Само наличие номера в JSON запроса без проверки текущего CRM-контакта и связи с карточкой разрешение не даёт. CRM-контакт, исходная карточка, имя и выбранный телефон фиксируются в контексте конкретного звонка. Доставка результата использует проверенный CRM-контакт этого звонка. Изменение локального телефона во время ожидания завершает заявку до резервирования ресурсов.

Удаление контакта в amoCRM блокирует связанные локальные записи для обзвона и фиксируется в аудите событием `contact.crm_deleted`. Записи остаются доступны в ATS вместе с историей. Обработчик webhook принимает JSON и form-данные и проверяет отдельный токен интеграции.

В таблице контактов и карточке клиента отображается отдельный запрет исходящих звонков. Администратор может снять его кнопкой «Разрешить звонки» в карточке активного контакта при действующем согласии и отсутствии номера в чёрном списке. Снятие запрета фиксируется в аудите событием `contact.unblocked`.

## 1. Обновить VPS

Выполнять **root на VPS**, когда тестовые разговоры завершены. Не копировать приглашение `root@...#` и строки с тройными обратными кавычками.

```bash
runuser -u ats-beta -- git -C /opt/ats-beta pull --ff-only origin main &&
bash /opt/ats-beta/deploy/ubuntu/update-beta.sh &&
git -C /opt/ats-beta rev-parse --short HEAD
```

Обновление делает backup и миграцию **0014**, проверяет отсутствие активных попыток и readiness. Asterisk не перезапускается.

Установить диалплан без 1, заменив плейсхолдеры двумя согласованными тестовыми номерами:

```bash
cd /opt/ats-beta
.venv/bin/python scripts/install-mobile-callback.py --manager-phone +7XXXXXXXXXX --customer-phone +7YYYYYYYYYY
asterisk -rx 'dialplan reload'
asterisk -rx 'dialplan show ats-beta-callback-customer'
```

В выводе нужен `State: ready`, приложения `Read` быть не должно. Скрипт сохраняет остальные настройки/секреты, добавляет только эти два направления в allowlist. Точные опубликованные V1/V2 обновляются автоматически с приватным backup; изменённый вручную блок не затирается.

## 2. Связать приватную интеграцию

В **ATOS → Настройки → amoCRM** сохранить:

| Поле | Значение |
|---|---|
| Поддомен | `omkr` |
| ID аккаунта | Можно оставить пустым при первичном сохранении: успешная «Проверить связь» или серверный установщик получит его из `/api/v4/account` |
| ID интеграции | UUID существующей приватной интеграции с этим виджетом |
| Секретный ключ | `client_secret` этой же интеграции; только в защищённое поле ATOS |
| Access token | Действующий токен API omkr; другое значение, не client secret |
| Mapping | Внутренний номер ATOS → реальный amo user ID каждого менеджера |

Для семи операторов — существующие extensions 702–708. Один amo user ID не назначается нескольким операторам. Пользователь ATOS активен, роль «оператор». В «Операторы/ACD» сохранить личные телефоны и поставить участникам теста «Свободен».

Origin redirect URI интеграции должен совпадать с `ATS_PUBLIC_ORIGIN`, например **`https://axiomats.ru`**. В `ratsUrl` — тот же HTTPS адрес. Затем:

```bash
cd /opt/ats-beta
.venv/bin/python scripts/configure-amo-widget.py --subdomain omkr
```

Скрипт проверяет encrypted profile/mapping и токен запросом `/api/v4/account`, сохраняет полученный числовой ID, связывает CRM с tenant телефонии и включает CRM без копирования секретов в env. После изменения env перезапустить beta API/worker-процессы, затем обновить страницу ATOS. Ранее явно указанный другой ID не заменяется автоматически: очистить ошибочное поле и повторить проверку. Access token хранится в encrypted profile или ранее настроенном env. Полный OAuth refresh flow не добавлен: истёкший access token обновляется в защищённых настройках.

Для нового или известного контакта согласие из действующей amoCRM выдаётся автоматически, как при фоновом импорте, так и при звонке из виджета. При ручном звонке виджет восстанавливает прежний локальный архив/блокировку после проверки активного CRM-контакта. Номер из явного чёрного списка отвергается с `contact_blacklisted`; удалённый контакт CRM не разрешается. Правила CSV/ручного импорта ATOS сохраняются. В preprod оба телефонных участника входят в `ATS_TEST_DESTINATIONS`. В AMI нужны PJSIP, `mcm-cli-`, назначение `8XXXXXXXXXX`, CLI 10 цифр, обработка ответа «Сценарий кампании», не Echo.

## 3. Подготовить WSS и SIP-устройства

```bash
cd /opt/ats-beta
.venv/bin/python scripts/install-widget-webrtc.py
```

Создаются отдельные SIP-устройства активных операторов; пароли шифруются в БД, приватный Asterisk include имеет `0640 root:asterisk`. Повторный запуск сохраняет пароли. Endpoints: `context=ats-beta-webrtc-deny`, `direct_media=no`, WebRTC/DTLS/ICE, RTP timeout 15 секунд. SIP From использует публичный домен вместо hostname сервера. HTTP Asterisk — на loopback:8088, WSS — через nginx.

В **существующий HTTPS server-блок домена ATOS** добавить:

```nginx
include /opt/ats-beta/deploy/ubuntu/nginx-asterisk-ws.conf;
```

Не заменять сайт и не добавлять строку вне server-блока. Затем:

```bash
nginx -t
systemctl reload nginx
asterisk -rx 'core reload'
asterisk -rx 'http show status'
asterisk -rx 'pjsip show transports'
asterisk -rx 'module show like res_srtp'
```

Ожидаются HTTP loopback:8088, `/ws`, transport `ats-beta-ws`. Уже используемый иной HTTP bind сохраняется, его upstream согласуется отдельно. Некоторые сборки добавляют transport только после перезапуска Asterisk — тогда нужен момент без разговоров, включая старую АТС. Публичный media IP и используемый RTP-диапазон должны быть достижимы. Настройки UDP-транка Multicom для браузерных endpoints менять не требуется.

## 4. TURN для офисных и мобильных сетей

Стенд проверяет TURN/TCP с временными HMAC credentials. Для отдельного coturn на том же VPS с назначенным интерфейсу публичным IPv4:

```bash
apt-get update
apt-get install -y coturn
cd /opt/ats-beta
.venv/bin/python scripts/install-widget-turn.py --public-ip PUBLIC_IPV4_ЭТОГО_VPS
```

Скрипт создаёт private shared secret и разрешает только Asterisk как relay peer. Уже используемый чужой coturn config не затирается. Открыть TCP 3478 и UDP 49160–49200 в firewall/экране хостера. Если используется UFW:

```bash
ufw allow 3478/tcp
ufw allow 49160:49200/udp
systemctl enable --now coturn
systemctl restart coturn
```

RTP Asterisk также остаётся доступен. Для VPS за NAT нужны отдельные external/relay IP и проброс портов. Сети, запрещающие TCP 3478, требуют TURN TLS на 5349 или отдельном 443 с сертификатом; `/asterisk/ws` не заменяет TURN.

Применить новый env к ATOS:

```bash
systemctl restart ats-beta-api ats-beta-worker@scheduler ats-beta-worker@telephony ats-beta-worker@inbox ats-beta-worker@crm
curl --fail --silent --show-error http://127.0.0.1:9130/health/ready
```

Сохранить preprod и тестовый allowlist до живой приёмки.

## 5. Загрузить архив и проверить

Загрузить `widget.zip` **5.3.1 в существующую приватную интеграцию**, сохранить `ratsUrl`, полностью перезагрузить все открытые вкладки amoCRM у менеджеров. Сначала обновить backend с миграцией 0014. Старый виджет 5.2 может звонить только при совпадении инициатора и ответственного; для другого ответственного сервер потребует обновление. В архиве нет SIP/AMI/OAuth секретов. JsSIP закреплён и собран локально; внешний CDN не нужен.

1. «На телефон ответственного»: видны имя/маска телефона менеджера. Ответить на мобильном, **ничего не нажимать**, дождаться клиента; проверить речь, завершение клиентом и автоматический «Свободен».
2. «В браузере amoCRM»: дождаться регистрации, разрешить микрофон, позвонить. Мобильный менеджера не вызывается. Проверить речь, кнопку завершения, длительность и освобождение.
3. Одна запись в ATOS, правильный контакт/менеджер в CRM. Очередь отправки не считается доказательством доставки: проверить реальную CRM-запись и ошибки очереди при истёкшем токене.
4. Занятость/отказ клиента, отмена до ответа менеджера, закрытие вкладки, двойное нажатие.
5. Нагрузка 1 → 4 → 7 менеджеров. Семь браузерных разговоров требуют 7 внешних каналов, семь мобильных — **14**. 15 DID не доказывают наличие 15 каналов: подтвердить ёмкость Multicom и общий лимит ATOS перед нагрузкой.

## Проверки 5.3.0

Проверены отдельные инициатор и участник в обоих режимах, ресурсы и занятость ответственного, повторная проверка владельца карточки, запрет готовности и приёма из чужой сессии, конфликт вкладок и истечение lease. SIP-пароль выдаётся только владельцу устройства. Один браузерный агент на оператора продлевает lease каждые несколько секунд; срок 90 секунд учитывает фоновые вкладки. Активный разговор не переносится в другую вкладку при истечении lease.

Native Chromium проверяет собственный звонок и две независимые сессии. Ответственный принимает вызов из списка контактов, инициатор не запрашивает микрофон и не создаёт RTCPeerConnection. Закрытие страницы инициатора после соединения сохраняет разговор ответственного. В обоих случаях проверяются TURN/TCP, медиапакеты в обе стороны, hangup, освобождение оператора и CRM-атрибуция.

На VPS владельца подтверждён собственный WebRTC-разговор 41 с, попытка `ac7b82c1-e7a9-4664-ab5e-3c32705fd0a1`, 22.11.2026 23:08–23:09 по Москве. Переход к другому ответственному в 5.3.0 проверен на изолированном стенде и требует проверки после обновления VPS и архива. Ранее созданные CRM-задачи автоматически не изменяются.

## Исправления 5.3.1 от 25.11.2026

Новая заявка amoCRM с уже известным номером больше не наследует запрет звонка из-за прежнего локального архива, блокировки или отсутствия согласия. Контакт проверяется через CRM, телефон и связь с карточкой сверяются, согласие устанавливается автоматически, затем создаётся одна одиночная кампания. Повторный запрос с тем же UUID не создаёт дубликаты. Чёрный список остаётся отдельным запретом, удалённые в CRM контакты не восстанавливаются по неподтверждённому запросу.

Кнопка завершения повторно ставит команду после неудачной попытки. При потере AMI-событий worker запрашивает полный коррелированный `CoreShowChannels`, проверяет `ATS_ATTEMPT_ID` и `UNIQUEID` через `Getvar`, завершает только принадлежащие попытке каналы и повторяет проверку. Частичный список, ошибки AMI, смена идентификатора или незавершённый Originate сохраняют резерв оператора. Пустой список сразу после Originate не считается окончательным доказательством: учитываются 30 секунд timeout плюс 15 секунд запаса. Успех разговора и его длительность не восстанавливаются по одному отсутствию каналов.

Тот же аккаунт на другом компьютере является другой сессией приёма. Управление собственным активным звонком доступно и из второй сессии; SIP-готовность по-прежнему принимает только сессия, которой назначен nonce.

Для зависшей попытки есть точечная команда. Сначала обновить исходники через `git pull --ff-only`; схема остаётся 0014. Чтение без изменений:

```bash
bash /opt/ats-beta/deploy/ubuntu/manage-beta.sh /opt/ats-beta/scripts/reconcile-widget-call.py --widget-call-id de980f48
```

Завершить только этот звонок и подтвердить отсутствие его каналов:

```bash
bash /opt/ats-beta/deploy/ubuntu/manage-beta.sh /opt/ats-beta/scripts/reconcile-widget-call.py --widget-call-id de980f48 --hangup
```

Префикс должен однозначно определять звонок в текущей организации. Команда проверяет также каналы ранее закрытой вручную записи, сохраняет её результат и не перезапускает Asterisk. Неполные доказательства оставляют резерв и сообщают о необходимости повторной проверки. Перед обычным `update-beta.sh` необходимо завершить или сверить активные попытки, как и раньше.
