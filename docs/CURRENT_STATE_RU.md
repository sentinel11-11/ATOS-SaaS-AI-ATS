# Состояние ATOS ATS по ТЗ 1.0

Проверено 21.11.2026 в облачной рабочей копии `/workspace/ATOS-SaaS-AI-ATS`, базовый commit `5fa3f3447bc6a27c464e88aa1eae8413479b2cab`. Результаты относятся к текущим изменениям поверх этого commit. Текущая работа сосредоточена на Мультикоме SIP/Asterisk и локальной подготовке фазы 1 по разделу 19 ТЗ.

По решению владельца от 21.11.2026 проверенные изменения публикуются прямым fast-forward push в `main`. GitHub Actions запускается на push. Результаты серверного применения и GitHub CI фиксируются после соответствующих проверок.

## Исправления

- Общая фикстура создаёт кампанию с маршрутом `multicom_ami`, tenant binding и явным списком тестовых направлений. Используются настоящий AMI-адаптер и локальный TCP-стенд. API и worker выполняют `validate_route`. Тесты завершения доставляют событие отдельно от подтверждения Originate.
- Перенесены изменения подтверждения DID и тестовой кампании из PR #7. Импортированные и новые номера Мультикома требуют подтверждения для активации. В интерфейсе доступны флаг подтверждения и provider `multicom_ami`.
- Новая кампания по умолчанию использует Мультиком, сообщение без шаблона, один канал и ноль повторов. Число каналов доступно в форме. Явно сохранённый ноль повторов сохраняется при открытии карточки.
- При включённом CLI prefix выбранный PJSIP endpoint проверяется до Originate. AMI Error приводит к `ami_endpoint_unavailable`. Серверный аккаунт требует write-класса `system` для `PJSIPShowEndpoint`. Добавлены профиль и инструкция настройки Мультикома.
- Воспроизведено сочетание успешного AMI Ping и отказа запуска с активным неподтверждённым А-номером. Вместо общего `ami_not_configured` API сообщает отдельные причины отсутствующего пароля, пустого пула, несовместимого провайдера и недопущенного номера. Интерфейс показывает пояснение API. Проверка AMI отображает отдельный результат допуска маршрута.
- Требование медиарежима для операторской кампании проверяется при старте через API v1 и v2. При отказе кампания сохраняет прежнее состояние. После явного подтверждения А-номера тест проходит от кнопки запуска до Originate через настоящий AMI-адаптер.
- Updater восстанавливает владельца `.venv` и переустанавливает локальный пакет после прерванной установки. Проверка активных попыток использует PostgreSQL напрямую. Генерация ключа выполняется от пользователя `ats-beta`. Регрессионный тест воспроизводит root-owned cache и отсутствие рабочего импорта приложения в disposable-контейнере.
- Таймлайн показывает сохранённую причину завершения и коды новых событий Hangup/OriginateResponse/DialStatus. CLI-диагностика конкретной попытки читает фактический AMI-профиль и выбранный endpoint. Скрипт сбора выполняет команды просмотра Asterisk, значения секретов в отчёт не включаются.
- Исправлен кеш AMI-конфигурации воркера. Сохранение tenant-профиля обновляет префикс и trunk следующего Originate без разрыва соединения. Смена параметров подключения приводит к переподключению. Добавлен тест смены сохранённого профиля с `mcm` на alias выбранного DID через реальный адаптер и TCP-стенд.
- Владелец подтвердил endpoint `mcm-cli-9690229926` с правильным From и отсутствие `system` в write-правах AMI. Подготовлен скрипт точечного добавления права выделенному аккаунту с backup и сохранением остальных параметров. В инструкции указан текущий порядок amoCRM-вызова, сначала клиент, затем SIP-устройство оператора; мобильный callback и operator-first ещё требуют реализации и UAT.
- Архивирование контакта устанавливает `archived` и `blocked`, отзывает consent под блокировкой tenant, как в существующем API v2. История попыток, связи кампаний, входящие звонки и CRM-связи сохраняются. Scheduler и dispatch проверяют признак архива перед новым вызовом.
- Терминальный webhook МегаФона без корректного номера после окна поиска сохраняется как `unmatched`. Создание исторического звонка требует нормализованного номера. Регрессионные случаи включают пустой, отсутствующий и некорректный номер.
- `cryptography` обновлена с `47.0.0` до `50.0.2`, транзитивная `opentelemetry-api` с `1.45.1` до `1.45.2`. Обновлён `uv.lock`.
- HTTP smoke использует настоящий AMI-адаптер и локальный TCP-стенд с проверкой Login. API и четыре worker-процесса работают отдельно. Стенд посылает повторное завершение и запоздалый ответ. Проверяются один Originate, выбранный Caller ID, alias `mcm-cli-9990000101`, одна попытка, дедупликация Inbox и одна CRM-задача.

## Воспроизведение

Выполнять из корня репозитория. Для облачной задачи используется существующая рабочая копия. Установка требует Docker, Python 3.12 и Node 24.

```bash
bash scripts/install-dev.sh
source scripts/dev-env.sh
```

Однократно создать disposable базы, если они ещё отсутствуют.

```bash
docker exec atos-dev-postgres createdb -U postgres ats_test
docker exec atos-dev-postgres createdb -U postgres ats_smoke
```

Запустить проверки.

```bash
export ATS_TEST_DATABASE_URL="postgresql+psycopg://postgres@/ats_test?host=$(pwd)/.runtime/pgsocket"
.venv/bin/pytest -ra
.venv/bin/ruff check src tests scripts migrations
npm --prefix frontend test
npm --prefix frontend run build
npm --prefix frontend audit --audit-level=moderate
XDG_CACHE_HOME=/workspace/.cache .venv/bin/pip-audit --cache-dir /workspace/.cache/pip-audit

export ATS_DATABASE_URL="postgresql+psycopg://postgres@/ats_smoke?host=$(pwd)/.runtime/pgsocket"
export ATS_LIVE_CALLS_ENABLED=false
.venv/bin/alembic upgrade head
.venv/bin/python scripts/smoke.py
.venv/bin/python scripts/check-database.py
```

Для проверки второго Python используется отдельная среда и отдельная база.

```bash
UV_PROJECT_ENVIRONMENT=.runtime/venv313 uv sync --frozen --python /usr/bin/python3.13
docker exec atos-dev-postgres createdb -U postgres ats_test313
ATS_TEST_DATABASE_URL="postgresql+psycopg://postgres@/ats_test313?host=$(pwd)/.runtime/pgsocket" \
  .runtime/venv313/bin/pytest -ra
```

`check-database.py` работает с базой `ats_smoke*`, создаёт уникальную временную базу восстановления и удаляет её после проверки. Исходную smoke-базу нужно освободить от пишущих процессов до сравнения. HTTP smoke завершает запущенные им процессы самостоятельно.

## Порядок отката этой итерации

Изменения используют схему `0011`. Для отката кода выбрать предыдущий проверенный release, установить зависимости из его lockfile и пересобрать frontend. Перед изменением серверного контура создать проверенный backup и снять состояние активных разговоров. Серверный порядок обновления и отката уточняется после inventory Asterisk и служб. В облачной проверке `.venv` Python 3.12 восстановлена после прерванного переключения интерпретатора, оба полных тестовых прогона выполнены заново в отдельных средах.
