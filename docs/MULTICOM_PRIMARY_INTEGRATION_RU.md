## Что делает код этапа 2

1. `ami.cli_endpoint_prefix=mcm-cli-` (по умолчанию выключено) включает явную маршрутизацию через PJSIP alias выбранного 10-значного А-номера, сохраняя один SIP-аккаунт и регистрационный профиль.
2. `ami.operator_number_map` задаёт для extension список разрешённых номеров. Когда карта не пуста, оператор без записи не получает общий номер автоматически.
3. Публичный click-to-call amoCRM требует точного однозначного `amo_user_id → extension → активный оператор ATOS` — без подмены на единственного свободного менеджера. Внутренний click-to-call для маршрута Multicom привязывается к текущему авторизованному оператору.
4. `POST /api/v1/workspace/numbers/import-multicom` создаёт только отсутствующие номера с `provider=multicom_ami`, `enabled=false`, `verified=false`. Существующие записи сохраняются, конфликт провайдера отвергается; операция защищена ролью admin, есть audit. Это **пакетный импорт, не live-синхронизация с Мультикомом**.
5. В Настройках добавлен импорт списка DID и сопоставление операторов ATOS (по extension) с подмножеством А-номеров.

## Операционная подготовка: PJSIP endpoint aliases

Исходный список 15 номеров должен быть сверенным с кабинетом или поддержкой Мультикома. Не добавлять произвольные Caller ID и не хранить SIP-пароли в репозитории.

```bash
cd /opt/ats-beta
python3 deploy/asterisk/build_mcm_cli_endpoints.py \
  --numbers-file /root/mcm-approved-dids.txt \
  --output /root/pjsip-mcm-cli.conf
```

Полученный файл нужно вручную проверить, установить как `/etc/asterisk/pjsip-mcm-cli.conf`, подключить через `#include "pjsip-mcm-cli.conf"` в `/etc/asterisk/pjsip.conf` и выполнить `pjsip reload` **только при отсутствии активных вызовов**. Перед изменениями создать резервные копии обоих PJSIP файлов.

Проверить все `pjsip show endpoint mcm-cli-XXXXXXXXXX`, убедиться в одной `mcm-reg: Registered`, проверить звонок с каждого разрешённого А-номера. Alias используют общие `mcm-auth`/`mcm-aor`, отдельной регистрации не создают.

После проверки aliases:

- В настройках AMI основной trunk — **`mcm`**, не `mcm-test`.
- Поле «Префикс endpoint А-номера» — `mcm-cli-` (до установки aliases оставлять пустым).
- В ATOS включать `verified`/`enabled` только для номеров, прошедших сверку и пробный вызов.
- Ротация использует существующий `select_caller` и записывает выбранный 10-значный Caller ID в `Attempt`, затем передаёт адрес alias в `__ATS_TRUNK`.
- При отсутствии соответствующего alias вызов не удаётся; автоматического отката на `mcm` с неподтверждённым А-номером нет.

## Операторы, amoCRM и А-номера

Разделить независимые сущности:

| Сущность | Пример | Назначение |
|---|---|---|
| `amo_user_id` | целочисленный ID amoCRM | Кто нажал «Позвонить» |
| ATOS `Operator.user_id` и `Operator.id` | UUID | Личный кабинет, статус, очередь |
| `Operator.extension` | `101` | SIP extension менеджера |
| `CallerNumber.phone` | `9690XXXXXX` | DID для исходящего `From` |

Существующая `amocrm.operator_user_map` связывает extension с amoCRM User ID. Новая `ami.operator_number_map` при необходимости связывает extension со списком разрешённых 10-значных DID. Пустая карта номеров означает общий пул. При непустой карте отсутствующий extension блокируется, а не получает случайный номер. Один DID может принадлежать нескольким операторам, один оператор может иметь несколько DID.

**Ограничение:** проверка существования amoCRM User ID через CRM API не удостоверяет личность вызывающего браузерного пользователя; для полной защиты публичного виджета требуется подписанная server-side идентификация пользователя. Разговорный операторский bridge/WebRTC ещё не готов и запрещён конфигурацией `ATS_MEDIA_ENABLED=false`.

## Настоящая синхронизация с Мультиком — не готова

SIP `REGISTER` и `pjsip show registrations` не возвращают перечень привязанных DID. Публичная документация MCM `https://wiki.mcm.ru/docs/api-endpoints/` перечисляет звонки, сотрудников и другие API, но не подтверждает отдельный метод «номера данного SIP-транка». Не путать MCM с MCN Telecom: их API и домены разные.

Для **настоящей** кнопки «Синхронизировать номера» нужны от поддержки Мультикома:

- документированный HTTPS endpoint GET/POST, авторизация и scope для чтения DID по данному trunk/аккаунту;
- пример JSON и идентификатор trunk для SIP учётной записи;
- способ узнать, какие DID разрешены как исходящий SIP `From`;
- режим пагинации/ETag, точная семантика удаления и ограничений доступа.

После получения контракта реализовать preview diff → подтверждение администратором → атомарный idempotent upsert; не удалять и не включать номера автоматически, не переносить из другого tenant. Пароли и API токены только в зашифрованных профилях.

## Необходимые до полного переключения следующие работы

- Отдельно реализовать operator-first/bridge `оператор ↔ клиент` со статусами, AMI событиями, CDR/CEL, записываемыми звонками, корректной обработкой Busy/NoAnswer/Hangup.
- Подключить проверенные SIP-extensions операторов или браузерный WebRTC.
- Добиться зелёного backend CI, live UAT по каждому А-номеру и ограничению 15 каналов.
- Отдельно проверить входящую маршрутизацию `from-mcm` и firewall UDP/RTP (в настоящее время UFW отключен). Не переключать входящие на неподготовленную цепочку.

## Откат

До подтверждения полностью готовой телефонии оставить основной боевой маршрут без изменения; `ami.cli_endpoint_prefix` по умолчанию пустой. В случае проблемы выключить новые кампании, вернуть пустой prefix в настройках, проверить `mcm-reg` и изолированно удалить временно подключённый include aliases при отсутствии звонков.
