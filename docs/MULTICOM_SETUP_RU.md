# Настройка Мультикома для первого вызова из ATOS

Рабочий маршрут — `multicom_ami`, SIP-транк Мультикома и PJSIP aliases `mcm-cli-<10 цифр>`. Подготовлены интерфейс подтверждения А-номера, выбор маршрута по умолчанию и локальные проверки полного пути API → scheduler → AMI → inbox → журнал.

## Серверный контур

В ТЗ зафиксированы VPS `89.223.127.145`, приложение `/opt/ats-beta`, Asterisk `20.6.0`, AMI `127.0.0.1:5038` и пользователь `ats-beta`. Последняя SSH-проверка из облачной среды к порту 22 получила `Connection refused`. Фактические параметры и состояние VPS ожидают проверки.

При доступном SSH выполнить инвентаризацию.

```bash
git -C /opt/ats-beta rev-parse HEAD
git -C /opt/ats-beta status --short
systemctl is-active asterisk ats-beta-api ats-beta-worker@scheduler ats-beta-worker@telephony ats-beta-worker@inbox ats-beta-worker@crm
asterisk -rx 'core show version'
asterisk -rx 'pjsip show registrations'
asterisk -rx 'pjsip show endpoints'
asterisk -rx 'dialplan show ats-beta'
asterisk -rx 'dialplan show ats-beta-answer'
asterisk -rx 'manager show command PJSIPShowEndpoint'
```

Параметры Мультикома для существующего environment-файла приведены в [deploy/multicom.env.example](../deploy/multicom.env.example). Внести tenant UUID, согласованное тестовое направление и действующий AMI secret через защищённую конфигурацию VPS. Проверить приоритет сохранённого AMI-профиля в настройках ATOS, включая `cli_endpoint_prefix`, host, port, user, TLS и secret. Tenant-профиль может переопределять соответствующие deployment-параметры.

## Обновление установленного интерфейса

Владелец подтвердил серверный commit `1c38954`. Формы подтверждения DID и новые диагностические сообщения доступны после установки текущего `main` и пересборки frontend. Перед обновлением проверить рабочую копию и сохранить имеющиеся локальные изменения.

```bash
cd /opt/ats-beta &&
runuser -u ats-beta -- git pull --ff-only origin main &&
bash deploy/ubuntu/update-beta.sh
```

Штатный updater проверяет чистоту рабочей копии, состояние активных попыток и поддерживаемую конфигурацию БД. После проверки создаёт backup, устанавливает зависимости, собирает frontend, применяет миграции и запускает beta-службы. Активные или неоднозначные попытки требуют предварительного завершения или сверки. После успешного обновления выполнить Ctrl+F5 в браузере и проверить новый commit командой `git -C /opt/ats-beta rev-parse --short HEAD`.

### Восстановление после прерванной установки зависимостей

При обновлении от 21.11.2026 установка остановилась на root-owned `cryptography/__pycache__`. После прерывания в виртуальном окружении отсутствовал пакет `ats`. Updater теперь восстанавливает владельца генерируемой `.venv`, проверяет активные попытки напрямую через PostgreSQL и принудительно переустанавливает локальный пакет `atos-ats` по lockfile. Генерация ключа при установке и обновлении выполняется от `ats-beta`.

Для восстановления окружения на версии updater, которая ещё импортирует `ats` до установки зависимостей, выполнить от root.

```bash
cd /opt/ats-beta &&
chown -hR ats-beta:ats-beta .venv &&
runuser -u ats-beta -- env UV_CACHE_DIR=/var/lib/ats-beta/.cache/uv \
  /opt/ats-beta-tools/installer/bin/uv sync --frozen --no-dev \
  --reinstall-package atos-ats --python /usr/bin/python3 &&
bash deploy/ubuntu/update-beta.sh
```

Сценарий восстановления проверяется в disposable-контейнере с настоящим PostgreSQL, root-owned каталогом bytecode и имитацией ошибки импорта приложения. Подтверждены успешный путь восстановления, сохранение владельца цели символьной ссылки и блокировка установки при активных попытках или ошибке SQL. Управление systemd, установка пакетов и HTTP health в этом тесте заменены контролируемыми командами.

## AMI отвечает, кампания отклоняется

Тест воспроизводит успешный AMI Login/Ping при активном А-номере с `verified=false`. Ранее запуск возвращал общий `ami_not_configured`. Текущий API возвращает конкретную причину и пояснение, а интерфейс выводит его при запуске кампании. Проверка AMI показывает также результат допуска маршрута.

| Код | Требуемое действие |
|---|---|
| `ami_secret_required` | Сохранить пароль AMI-аккаунта в профиле Asterisk ATOS |
| `caller_pool_empty` | Добавить и подтвердить А-номер или настроить разрешённый Caller ID |
| `caller_number_not_verified` | Подтвердить активный номер после проверки права использования у Мультикома |
| `caller_number_provider_mismatch` | Установить для номера provider `multicom_ami` |
| `caller_pool_unavailable` | Проверить включение номера, разрешение исходящих и карантин |
| `media_not_configured` | Подготовить медиарежим для операторского сценария или выбрать одиночный тест «Информатор» без шаблона |

Для первого прогона использовать тот же разрешённый А-номер и endpoint, с которыми успешен прямой тест на сервере. Значение «Активен» и подтверждение права использования — отдельные поля карточки. Режим «Перевод на операторов» проходит дополнительную проверку медиарежима при запуске.

## Диагностика завершившегося вызова

В таймлайне отображается сохранённая причина завершения. Для новых AMI-событий сохраняются числовые коды Hangup и OriginateResponse, а также нормализованный DialStatus. Исторические строки показывают сведения, сохранённые на момент события.

`ami_hangup_fallback` означает получение Hangup от Asterisk для связанного канала. Сам код требует уточнения по маршруту, загруженному диалплану и коду завершения Asterisk. Доступ к профилю, настройки endpoint и SIP-результат проверяются по конкретному вызову.

Для сбора данных выполнить от root, указав UUID попытки из журнала.

```bash
bash /opt/ats-beta/deploy/ubuntu/diagnose-multicom.sh CALL_UUID
```

Скрипт читает существующую попытку и текущий tenant-профиль AMI, затем выполняет `dialplan show` для его исходящего и ответного контекстов и `pjsip show endpoint` для выбранного endpoint. А-номер берётся из сохранённой попытки, параметры маршрута — из текущей конфигурации. Отчёт содержит открытые параметры маршрута и признак наличия AMI secret. Значения секретов в вывод не включаются. Скрипт выполняет чтение и команды просмотра Asterisk.

## Проверка endpoint перед Originate

При `ATS_AMI_CLI_ENDPOINT_PREFIX=mcm-cli-` адаптер выполняет `PJSIPShowEndpoint` для выбранного alias перед каждым Originate. Ответ AMI Error приводит к `ami_endpoint_unavailable`, отправка Originate прекращается. Ошибка включает как отсутствие alias, так и отказ AMI в выполнении проверки. Проверка успешного ответа подтверждает наличие endpoint в Asterisk.

Действию `PJSIPShowEndpoint` требуется AMI write-класс `system`. В образце аккаунта указано `write = originate,call,system`, loopback ACL и `read = call,user`. Сопоставить эти права с установленной версией Asterisk и применить согласованную конфигурацию к выделенному аккаунту ATOS перед включением ротации. Основание для класса доступа проверено в регистрации действия в исходниках Asterisk 20. [Исходники Asterisk](https://github.com/asterisk/asterisk/blob/20/res/res_pjsip/pjsip_configuration.c)

### Подтверждённые настройки VPS и исправление маршрута

В отчёте владельца от 21.11.2026 выбран endpoint `mcm` с `from_user=00083819`, а сохранённый tenant-профиль содержит пустой `cli_endpoint_prefix`. Отдельный endpoint `mcm-cli-9690229926` существует и имеет `from_user=9690229926`. У AMI-пользователя `ats-beta` фактические write-права `call,originate`, поэтому проверка alias через `PJSIPShowEndpoint` требует добавления `system`.

Из корня обновлённого репозитория выполнить от root.

```bash
python3 scripts/enable-ami-endpoint-check.py &&
asterisk -rx 'manager reload'
asterisk -rx 'manager show user ats-beta' | grep -i perm
```

Скрипт находит секцию `ats-beta` в `manager.conf` и его включениях, добавляет `system` к существующей строке write, сохраняет остальные параметры и создаёт backup с правами `0600`. При неоднозначной или наследуемой конфигурации изменение отклоняется. Значения секретов в вывод не включаются. После reload и обновления beta новые AMI-соединения используют обновлённые права.

В ATOS открыть «Настройки → Asterisk AMI Manager», установить «Префикс endpoint А-номера (ротация)» в `mcm-cli-` и сохранить все настройки. Это значение требуется именно в tenant-профиле, поскольку сохранённая пустая строка переопределяет environment. Для первого звонка оставить один подтверждённый активный DID `9690229926`.

Исправлена ошибка кеширования AMI-настроек в воркере. Изменение префикса или trunk теперь применяется к следующему Originate с сохранением AMI-соединения. Изменение параметров подключения закрывает старое соединение и открывает новое при следующем обращении. Регрессионный тест меняет сохранённый профиль и проверяет переход с `mcm` на `mcm-cli-<DID>` через настоящий AMI-адаптер и локальный TCP-стенд.

## Порядок звонка из amoCRM в текущем коде

Кнопка виджета определяет оператора через mapping amoCRM и создаёт одиночную операторскую кампанию. Scheduler резервирует этого оператора. AMI набирает телефон клиента через выбранный alias Мультикома. После ответа клиента медиасценарий вызывает `Dial(PJSIP/${ATS_OPERATOR_EXT},30)`, где extension должен соответствовать SIP-устройству менеджера в Asterisk.

Таким образом, текущий путь сначала набирает клиента, затем SIP-устройство менеджера. Обратный вызов на обычный мобильный менеджера и отдельный сценарий operator-first ещё требуют реализации. Рабочий разговорный мост пока не подтверждён live UAT. Одиночный тест «Информатор → Без шаблона» при выключенном медиарежиме воспроизводит клиенту `hello-world` и завершает звонок.

## Импорт и подтверждение пула

1. Импортировать разрешённые номера через настройки Мультикома. Повторный импорт сохраняет существующие flags. Новые записи имеют provider `multicom_ami`, `verified=false`, `active=false`.
2. В карточке одного согласованного А-номера выбрать «Мультиком SIP / Asterisk», подтвердить право использования у оператора и установить флаг подтверждения.
3. Для этого номера разрешить исходящие вызовы и включить участие в ротации. Сохранить карточку. API проверяет подтверждение перед активацией.
4. Сверить номер карточки, имя PJSIP alias и фактический From. Остальные номера вводить после индивидуальной проверки.

### Ограниченный тест Echo из ATOS

Установка добавляет только контекст `ats-beta-echo` в существующий beta-диалплан с резервной копией. Проверяются наличие приложения Echo, функции TIMEOUT, базовых beta-контекстов и отсутствие конфликтующей версии Echo. Установку выполнить от root из обновлённого репозитория.

```bash
python3 scripts/install-multicom-echo-test.py &&
asterisk -rx 'dialplan reload' &&
asterisk -rx 'dialplan show ats-beta-echo'
```

В настройках AMI выбрать «Обработка после ответа → Тест звука Echo — до 30 секунд» и сохранить все настройки. Выбор применяется ко всем исходящим кампаниям Мультикома рабочего пространства. Приостановить остальные кампании и запустить только одну проверку «Информатор → Без шаблона», один контакт, один канал, ноль повторов.

Принять вызов на телефоне, произнести фразу и проверить возврат собственного голоса. Echo заканчивается по `#`, при завершении звонка или по абсолютному таймеру 30 секунд после ответа сети. AGI и TTS для этого контекста не требуются. Перед обычными кампаниями вернуть «Обработка после ответа → Сценарий кампании». Кампании с оператором или шаблоном при выбранном Echo отклоняются до набора.

Если вызов снова исчезнет до принятия, собрать новую SIP-трассу этой попытки. Подтверждение сети и фактический ответ человека фиксируются отдельно. Ротация и охлаждение требуют следующих тестов после проверки звука на одном DID.

Локально проверены сохранение профиля, параметр Context в настоящем AMI-адаптере, ограничения запуска, установка с backup и обработка отсутствующего приложения/таймера. Нативный Echo на VPS и возврат звука человеку ещё предстоит проверить. Попытка установить Asterisk в отдельный локальный контейнер остановилась на HTTP 403 от APK-репозитория; такой прогон не учитывается как успешная проверка Asterisk.

## Подготовка операторского режима

Для «Перевода на операторов» требуются установленный `ats_beta.py` в AGI-каталоге Asterisk, общая директория `/var/lib/ats-beta-media`, медиаветка в загруженном `ats-beta-answer`, свободный оператор ATOS и его рабочий PJSIP extension. Подготовку файлов и зависимостей выполняет `deploy/asterisk/install-beta-media.sh` на VPS.

После проверки этих условий установить `ATS_MEDIA_ENABLED=true` в `/etc/ats-beta/ats.env`. При применении флага перезапустить beta API и beta workers, чтобы проверка старта и dispatch использовали новое значение. Запуск API через systemd читает deployment env при старте процесса.

Для одиночной проверки «Информатора» очистить шаблон в карточке кампании. В локальной проверке существующая операторская кампания после сохранения `flow=message`, `template_id=null` успешно стартует при `ATS_MEDIA_ENABLED=false` и отправляет один Originate с `__ATS_MEDIA=0` на AMI TCP-стенд.

## Локальные доказательства

Общие тестовые кампании используют маршрут Мультикома и локальный AMI TCP-стенд. HTTP smoke импортирует синтетический DID, проверяет отказ активации до подтверждения, подтверждает и активирует номер, проверяет endpoint и выполняет один Originate. Повторные и запоздалые события проходят Inbox. Тесты отказа проверяют неверный AMI secret и недоступный endpoint.

Команды локального прогона и текущий результат приведены в [CURRENT_STATE_RU.md](CURRENT_STATE_RU.md). Для одного DID владелец предоставил серверную трассу вызова и подтверждение отображения Caller ID. Проверки всего пула, RTP, разговора оператор ↔ клиент и CDR/CEL ещё предстоят.
