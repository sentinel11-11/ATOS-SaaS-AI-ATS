# Разговор через личный телефон менеджера

Мультиком/Asterisk поддерживает операторскую кампанию с двумя внешними плечами. ATOS сначала звонит менеджеру. Менеджер отвечает, слышит короткий сигнал и нажимает **1** в течение 15 секунд. ATOS повторно проверяет кампанию, согласие контакта, номера участников и допуск А-номера, затем разрешает Asterisk набрать клиента. После ответа клиента участники разговаривают через Asterisk. Оба видят выбранный А-номер Мультикома.

Оператор закрепляется за попыткой до первого набора. Его ответ не устанавливает успешный ответ клиента. Разговор подтверждается пересечением времени нахождения обоих физических каналов в мостах Asterisk. Режим использует Local `/n`, поэтому два связанных моста сохраняются на весь разговор. Завершение требует результата сценария и закрытия обоих внешних плеч; один Hangup не освобождает оператора.

## Установка на существующем VPS

Нужны действующий SIP-транк, зарегистрированные CLI aliases `mcm-cli-<10 цифр>`, проверенный двусторонний RTP и доступный AMI с `read=call,user`, `write=originate,call,system`. Оба номера участников должны отличаться. На счёте Мультикома должны быть доступны два одновременных исходящих вызова. Конфигурация SIP-авторизации остаётся в Asterisk.

Перед обновлением закончить активные вызовы и остановить прочие кампании для контрольного теста. Ниже синтетические примеры номеров; заменить их согласованными номерами менеджера и клиента. Выполнять от root в `/opt/ats-beta`.

```bash
cd /opt/ats-beta &&
runuser -u ats-beta -- git pull --ff-only origin main &&
.venv/bin/python scripts/install-mobile-callback.py --manager-phone +79990001000 --customer-phone +79990000101 &&
asterisk -rx 'dialplan reload' &&
bash deploy/ubuntu/update-beta.sh
```

Установщик проверяет нужные приложения Asterisk и функцию `STAT`, добавляет контексты в существующий `/etc/asterisk/extensions-ats-beta.conf`, создаёт сигнал подтверждения и каталог записей, даёт пользователю `ats-beta` членство в группе `asterisk`. Ранее опубликованный неизменённый callback v1 обновляется до v2 с backup; проверяется SHA-256 всего исходного блока. Остальные контексты, включая Echo, сохраняются. Изменённые вручную контексты требуют разбора. В `/etc/ats-beta/ats.env` устанавливается `ATS_CALLBACK_ENABLED=true`, оба направления добавляются к существующему `ATS_TEST_DESTINATIONS`. Остальные строки и секреты, владелец и права конфигурации сохраняются; backups имеют права `0600`. Сам установщик вызовы не запускает. Updater применяет миграцию `0012` и перезапускает только beta-службы; Asterisk не перезапускается.

В v1 `Read` искал `ats-beta/callback-ready` относительно каталога данных Asterisk. На VPS каталог данных — `/usr/share/asterisk`, а установщик создаёт WAV в `/var/lib/asterisk/sounds/ats-beta`. Воспроизведён мгновенный `operator_not_confirmed` при несовпадении каталогов. В v2 используется абсолютный путь к установленному WAV. Отсутствие файла проверяется до `Read` и получает причину `callback_prompt_unavailable`; ошибка `READSTATUS=ERROR` — `callback_confirmation_failed`. Для применения исправления после `git pull` повторно выполнить установщик и `dialplan reload`, затем updater. Простое обновление кода не заменяет загруженный диалплан.

Проверить загрузку контекстов:

```bash
asterisk -rx 'dialplan show ats-beta-callback-operator'
asterisk -rx 'dialplan show ats-beta-callback-customer'
```

## Настройка первого разговора в ATOS

1. В «Настройки → Asterisk AMI Manager» выбрать обработку после ответа **«Сценарий кампании»**, сохранить. Префикс endpoint должен быть `mcm-cli-`, технология — PJSIP. Проверить допуск маршрута. Ранее выбранный тест Echo блокирует операторские кампании.
2. В «Операторы / ACD» у выбранного менеджера открыть «Настроить подключение», выбрать **«Личный телефон — сначала звонок менеджеру»**, сохранить его номер. Установить статус «Свободен».
3. В общих лимитах ATOS должно быть минимум **два внешних канала**. В пуле включить проверенный DID с доступным дневным бюджетом и завершённым охлаждением. Если настроены индивидуальные А-номера операторов, добавить этот DID в разрешения выбранного менеджера.
4. Создать кампанию: Мультиком AMI, **«Перевод на операторов (ACD)»**, **«Без шаблона»**, явно выбрать этого менеджера, один одновременный звонок, ноль повторов. Расписание должно включать время теста в часовом поясе tenant.
5. Добавить один контакт с номером второго участника и подтверждённым согласием. Номер менеджера в контакты этой кампании не добавлять. Запустить кампанию.
6. Ответить на телефоне менеджера, нажать **1**. Дождаться вызова на телефон клиента. Ответить вторым участником, поговорить в обе стороны и завершить вызов одним из участников.

Ожидается одна попытка в журнале, два плеча в таймлайне, результат `completed` и длительность от соединения участников до размыкания моста. После закрытия обоих плеч менеджер свободен, активный вызов исчезает. При включённой и настроенной CRM создаётся одна задача выгрузки результата. Записи зависят от `ami_record_calls`; после закрытия файла их подбирает worker (пауза минимум 10 секунд). Текущий импорт WAV ограничен 10 MiB; длинные записи требуют отдельного расширения.

Если менеджер не ответил, занят или не нажал 1, клиент не набирается. Если клиент занят или не ответил, менеджерское плечо завершается, попытка получает соответствующую причину. Если события потеряны или противоречат друг другу, итог — `unknown`: оператор и два канала остаются зарезервированы до сверки Asterisk/CDR/CEL и ручного решения с evidence. Watchdog и массовое закрытие не подменяют эту сверку.

## Лимиты и ротация

Один разговор через мобильный занимает **два** внешних канала tenant, **один** слот кампании и резервирует **две** единицы дневного бюджета выбранного А-номера. Бюджет резервируется консервативно до набора менеджера и не возвращается при отказе второго плеча. В журнале остаётся одна бизнес-попытка. Для обоих плеч используется один и тот же А-номер; ротация происходит между бизнес-попытками. Охлаждение запускается при резервировании попытки. Это ограничение частоты, а не гарантия отсутствия операторских спам-меток.

Установка не включает AGI/TTS: мобильный callback без шаблона использует собственный диалплан. SIP-операторы, ИИ-сценарии и шаблоны продолжают требовать медиарежим. Встраиваемый WebRTC-клиент amoCRM остаётся следующим этапом; существующий mapping amoCRM должен указывать на оператора ATOS с выбранным способом подключения.

## Проверки и откат

Автотесты проверяют резервирование, квоты и ёмкость, повторные проверки перед клиентом, раздельные ответы участников, завершение обоих плеч, одну CRM-задачу, занятость и отсутствие подтверждения. Отдельный контейнер Asterisk **20.21.0**, закреплённый digest, проходит настоящий AMI → SIP → RFC4733 → два моста → RTP в обе стороны как со стандартным каталогом данных, так и с `/usr/share/asterisk`. SIP-пир работает на loopback с синтетическими номерами. Отдельно проверяются занятость менеджера, занятость клиента, завершение без 1, полное ожидание 15 секунд и отсутствие файла сигнала с технической причиной. Серверный live UAT описан выше; остальные DID и предельная ёмкость транка Мультикома требуют отдельных проверок.

```bash
docker exec atos-dev-postgres createdb -U postgres ats_test_native
docker pull andrius/asterisk:20@sha256:05391d46660b1dcadd193e265758fb06a785ad484b7add2a0cb0ba5e50a76929
PYTHONPATH=tests ATS_TEST_DATABASE_URL="postgresql+psycopg://postgres@/ats_test_native?host=$(pwd)/.runtime/pgsocket" \
  .venv/bin/pytest tests/native/callback_smoke.py -ra
```

Стенд сохраняет `.runtime/callback-native-*.log` и JSON состояния SIP-пира. Он также включён отдельным заданием `native-callback` в GitHub Actions.

Миграция `0012` сохраняет старые вызовы как `standard` с одной единицей нагрузки. Downgrade к `0011` допустим только пока мобильная конфигурация и история callback отсутствуют. После их появления миграция отклоняет удаление данных. Откат кода потребует совместимого со схемой `0012` приложения и учёта двух плеч: прежний release проверяет readiness только для `0011` и не учитывает второй канал. При проблеме остановить новые операторские кампании, сверить физические вызовы и сохранить схему/историю до исправленного release. Перед восстановлением конфигурации из backup сначала сверить отсутствие активных физических каналов.
